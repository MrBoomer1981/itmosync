# ТЗ: `itmosync` — синхронизация расписания my.itmo → Apple Calendar

**Версия:** 1.0
**Дата:** 11.09.2026
**Исполнитель:** Claude Code
**Язык интерфейса и сообщений:** русский. Код, имена, коммиты — английский.

---

## 1. Цель

CLI-утилита для macOS, которая забирает личное расписание занятий из my.itmo и
поддерживает его в актуальном состоянии в отдельном календаре iCloud.
Запускается вручную примерно раз в неделю.

**Главное требование — идемпотентность.** Повторный запуск не должен порождать
дубликаты, а изменение пары должно приводить к обновлению существующего
события, а не к паре «удалил + создал».

---

## 2. Границы

### Входит в эту версию

- Авторизация в my.itmo по refresh-токену
- Получение расписания на скользящее окно 28 дней
- Создание, обновление и удаление событий в календаре iCloud через CalDAV
- Отчёт о прогоне в терминал
- Режим `--dry-run`

### НЕ входит (следующие версии, не проектировать заранее)

- Телеграм-бот
- Поиск городских мероприятий и конференций
- Автоматический логин по логину/паролю ИСУ
- Запуск по расписанию через `launchd`
- Веб-интерфейс, ICS-эндпоинт, поддержка не-Apple календарей

Архитектура не должна усложняться ради этих пунктов, но и не должна им мешать:
достаточно того, что `sync.py` не завязан на способ вывода отчёта.

## 5. Шаг 1 обязателен: разведка API

**Кода до выполнения этого шага не писать.**

Внутренний API my.itmo не задокументирован. Разработчик (или пользователь по
инструкции разработчика) открывает my.itmo в браузере с открытой вкладкой
Network и фиксирует в `docs/api-notes.md`:

1. Точный URL запроса расписания: путь, все query-параметры, формат дат
2. Все заголовки запроса, включая формат заголовка `Authorization`
3. Полный JSON ответа за неделю с парами разных типов — сохранить в
   `tests/fixtures/schedule_sample.json`, **предварительно заменив ФИО
   преподавателей, номер ИСУ и номер группы на вымышленные**
4. Точные строковые значения поля типа занятия («Лекции», «Практические
   занятия», «Лабораторные работы» и так далее) — они пойдут в словарь маппинга
5. Как выглядит онлайн-пара: где лежит ссылка на созвон, как помечается
6. URL token-эндпоинта ITMO ID и формат ответа при `grant_type=refresh_token`

Refresh-токен добывается один раз в консоли браузера на my.itmo:

```js
decodeURI(document.cookie.split('auth._token.itmoId=')[1].split(';')[0])
```

Схемы pydantic пишутся **под реально зафиксированный ответ**, а не под догадку.
Если фактическая структура расходится с этим ТЗ — источником истины является
`api-notes.md`, ТЗ правится следом.

## 6. Конфигурация и секреты

### Конфиг

Файл `~/.config/itmosync/config.toml`, создаётся командой `itmosync init`.

```toml
[calendar]
name = "ИТМО · Пары"
timezone = "Europe/Moscow"
caldav_url = "https://caldav.icloud.com/"
apple_id = "user@example.com"

[sync]
window_days = 28
reminder_minutes = 0          # 0 = напоминаний нет (решение по умолчанию)
online_link_in_location = true # ссылка на созвон в поле "Место"
delete_threshold = 0.5        # доля удалений, выше которой нужен --force

[lesson_types]
"Лекции" = "лек"
"Практические занятия" = "пр"
"Лабораторные работы" = "лаб"
"Консультация" = "конс"
"Экзамен" = "экз"
```

Неизвестный тип занятия не считается ошибкой: берётся первое слово исходной
строки в нижнем регистре, в лог пишется предупреждение с точной строкой, чтобы
её можно было добавить в конфиг.

### Секреты

Только macOS Keychain через `keyring`, сервис `itmosync`:

- `itmo_refresh_token`
- `apple_app_password` — пароль приложения Apple ID, не основной пароль

**Запрещено:** писать секреты в конфиг, в SQLite, в логи, в вывод отчёта, в
сообщения об ошибках. Логгер обязан маскировать любую строку длиннее 20
символов, похожую на токен, до вида `abcd…wxyz`.

## 7. Доменная модель

```python
class LessonType(StrEnum):
    LECTURE = "лек"
    PRACTICE = "пр"
    LAB = "лаб"
    CONSULT = "конс"
    EXAM = "экз"
    OTHER = "зан"

@dataclass(frozen=True, slots=True)
class Lesson:
    date: datetime.date
    start: datetime.time
    end: datetime.time
    subject: str
    type: LessonType
    raw_type: str              # исходная строка из API, как есть
    teacher: str | None
    room: str | None
    building: str | None
    address: str | None
    online_url: str | None
    group: str | None
    note: str | None
    index: int                 # см. ниже
```

`index` — порядковый номер пары среди занятий с одинаковыми
(дата, предмет, тип) в этот день, начиная с 0. Считается после сортировки по
времени начала. Нужен, чтобы две лекции по одному предмету в один день не
схлопнулись в одно событие.

## 8. Ключи идентичности

Два разных ключа, и их нельзя путать — это центральное решение всего проекта.

### UID — якорь события, меняется редко

```python
uid_key = f"{date:%Y-%m-%d}|{normalize(subject)}|{type.value}|{index}"
UID = f"itmo-lesson-{sha1(uid_key.encode()).hexdigest()[:16]}@itmosync"
```

`normalize()` — нижний регистр, схлопывание пробелов, удаление кавычек и
концевой пунктуации.

**В UID НЕ входят:** время, аудитория, корпус, преподаватель, ссылка.
Если бы они входили, смена аудитории означала бы удаление события и создание
нового — пользователь увидел бы в телефоне «событие удалено», а история
уведомлений сбросилась бы.

### X-ITMO-HASH — хэш содержимого, решает «обновлять или нет»

```python
content_key = "|".join([
    start.isoformat(), end.isoformat(), subject, raw_type,
    room or "", building or "", teacher or "", online_url or "",
])
X-ITMO-HASH = sha1(content_key.encode()).hexdigest()[:16]
```

Хранится как X-property внутри самого VEVENT. Отдельной базы для этого не нужно.

## 9. Формат события

| Поле iCalendar | Содержимое |
|---|---|
| `SUMMARY` | `{предмет} · {тип} · {аудитория}`. Без аудитории → `{предмет} · {тип}`. Онлайн → `{предмет} · {тип} · онлайн` |
| `DTSTART` / `DTEND` | С `TZID=Europe/Moscow`. Плавающее время не использовать |
| `LOCATION` | Онлайн-пара и `online_link_in_location = true` → URL созвона. Иначе `Ауд. {room}, {building}` плюс адрес, если он есть |
| `DESCRIPTION` | Построчно: преподаватель; исходный тип занятия; ссылка на созвон; группа; примечание. Последней строкой — `Синхронизировано itmosync, {дата и время}` |
| `URL` | Ссылка на созвон, если есть |
| `CATEGORIES` | `ИТМО` |
| `STATUS` | `CONFIRMED` |
| `TRANSP` | `OPAQUE` |
| `X-ITMO-HASH` | См. раздел 8 |
| `X-ITMO-SOURCE` | `my.itmo` |
| `VALARM` | Только если `reminder_minutes > 0`. По умолчанию отсутствует |

В календарь пишется корректный VTIMEZONE для Europe/Moscow.

## 10. Алгоритм синхронизации

```
1. window = (сегодня, сегодня + window_days)
2. desired  = itmo.schedule.fetch(window)        → dict[UID, Lesson]
3. existing = icloud.list_owned(window)          → dict[UID, (href, hash)]
   ── в existing попадают ТОЛЬКО события, чей UID совпал с
      ^itmo-lesson-[0-9a-f]{16}@itmosync$
4. to_create = desired.keys()  - existing.keys()
   to_delete = existing.keys() - desired.keys()
   to_update = {uid | uid в обоих и hash различается}
5. проверки безопасности (раздел 11)
6. если --dry-run: напечатать план, выйти с кодом 0, ничего не записав
7. применить: сначала create, потом update, потом delete
8. напечатать отчёт
```

### Обязательные предохранители

Оба срабатывают **до** записи и оба обязательны.

1. **Пустой ответ API.** Если `desired` пуст, а `existing` — нет, синхронизация
   прерывается с ошибкой «API вернул пустое расписание, календарь не тронут».
   Это защита от обнуления календаря при сломавшемся API или протухшем токене,
   который отдал 200 с пустым телом. Обходится только флагом `--force`.

2. **Массовое удаление.** Если `len(to_delete) / max(len(existing), 1)` больше
   `delete_threshold`, работа прерывается с показом списка того, что
   собирались удалить, и предложением перезапустить с `--force`.

3. **Область действия.** Ни одна операция записи или удаления не выходит за
   пределы окна и за пределы маски UID. События в том же календаре, созданные
   вручную, не читаются, не изменяются и не удаляются.

## 11. CLI

Точка входа — `itmosync`.

| Команда | Поведение |
|---|---|
| `itmosync init` | Создаёт конфиг с дефолтами, спрашивает Apple ID и имя календаря |
| `itmosync auth --set-token` | Принимает refresh-токен из stdin (не из аргумента — он попадёт в history), кладёт в Keychain, сразу проверяет обменом на access |
| `itmosync auth --set-apple-password` | То же для пароля приложения Apple ID |
| `itmosync doctor` | Проверяет по пунктам: конфиг читается; refresh-токен обменивается; API расписания отвечает; iCloud доступен; календарь найден или может быть создан; таймзона корректна. Печатает чек-лист с ✓/✗ |
| `itmosync sync [--days N] [--dry-run] [--force] [--verbose]` | Основная команда |
| `itmosync show [--week \| --days N]` | Печатает расписание таблицей, в календарь не пишет. Полезно для проверки парсера отдельно от записи |

**Коды возврата:** `0` успех · `2` ошибка конфигурации · `3` ошибка
авторизации · `4` ошибка API расписания · `5` ошибка календаря ·
`6` сработал предохранитель · `1` прочее.

## 12. Ошибки

```
ItmosyncError
├── ConfigError
├── AuthError
│   ├── TokenExpiredError      # refresh мёртв, нужен новый
│   └── TokenRejectedError     # сервер не принял токен
├── ItmoApiError
│   ├── ScheduleSchemaError    # ответ не лёг в модель
│   └── RateLimitError
├── CalendarError
│   ├── CalDavAuthError
│   └── CalendarNotFoundError
└── SafetyGuardError           # сработал предохранитель
```

Требования к сообщениям: на русском, говорят что делать. `TokenExpiredError`
печатает готовую инструкцию, как достать новый токен из браузера, включая
строку для консоли.

`ScheduleSchemaError` обязан показать, какое именно поле не сошлось и кусок
сырого JSON вокруг него — иначе отладка изменившегося API превращается в
угадайку.

HTTP: таймаут 15 с, три ретрая с экспоненциальной задержкой на 5xx и сетевые
сбои, без ретраев на 4xx.

## 14. Порядок реализации

Каждый шаг завершается рабочим состоянием и зелёными тестами. Не начинать
следующий, пока предыдущий не закоммичен.

1. **Разведка API.** `docs/api-notes.md` и анонимизированная фикстура. Кода нет.
2. **Каркас.** `pyproject.toml`, структура пакетов, `config.py`, `errors.py`,
   `logging.py`, команды `init` и пустой `doctor`. Ruff и mypy зелёные.
3. **Авторизация.** `itmo/auth.py`, команды `auth`. `doctor` умеет проверять
   токен. Тесты на respx.
4. **Чтение расписания.** `itmo/client.py`, `itmo/schedule.py`, `models.py`,
   команда `show`. На этом шаге расписание уже видно в терминале — есть что
   проверить глазами до всякого CalDAV.
5. **Маппинг в VEVENT.** `ical/mapper.py` плюс `test_mapper_golden`. Календарь
   ещё не трогаем.
6. **CalDAV.** `ical/icloud.py`, подключение, создание календаря, чтение окна.
   `doctor` проверяет iCloud.
7. **Диф и запись.** `sync.py`, предохранители, `report.py`, команда `sync`.
   Весь набор тестов из раздела 13.
8. **README.** Установка, первый запуск, где взять оба секрета, что делать при
   протухшем токене.

Первый реальный запуск на живом календаре — только через `--dry-run`.

## 16. Правила для разработчика

- URL my.itmo живут **только** в `itmo/client.py`. Ни одной строки с адресом в
  другом модуле.
- `cli.py` не содержит логики: разбор аргументов, вызов, вывод.
- Любая операция удаления проходит через одну функцию, которая проверяет маску
  UID. Второго пути к удалению в коде быть не должно.
- Все даты и время — timezone-aware. Наивный `datetime` в коде запрещён.
- Пакет с календарной логикой называется `ical`, не `calendar` — иначе конфликт
  с модулем стандартной библиотеки.
- Фикстуры не содержат настоящих ФИО, номера ИСУ и номера группы.

## Приложение. Решения, принятые по умолчанию

Меняются одной строкой конфига, вынесены отдельно, чтобы было видно, что это
выбор, а не случайность.

| Решение | Значение | Почему |
|---|---|---|
| Напоминания о парах | Выключены (`reminder_minutes = 0`) | Расписание и так известное, лишние уведомления раздражают |
| Ссылка на созвон | В поле «Место» | Кликабельна прямо из уведомления и из виджета, не нужно открывать событие |
| Источник истины | Календарь, не база | Убирает рассинхрон «в базе одно, в iCloud другое»; SQLite в этой версии не нужен вообще |
| Горизонт | 28 дней | Перекрывает пропущенную неделю; дальше заглядывать бессмысленно, переносы появляются ближе к дате |
| Исчезнувшие пары | Удаляются, перечисляются в отчёте | Календарь совпадает с my.itmo, но отмена не проходит незамеченной |
